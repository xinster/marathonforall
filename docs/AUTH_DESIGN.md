# 用户登录 / 账号体系设计方案

> 状态:**设计草案,未实施** · 2026-10-08
> 前置阅读:`docs/HANDOVER.md`(红线 3 数据契约、红线 6 唯一状态引擎)
> 相关代码:`marathon-platform/assets/store.js`(`[SEAM]` 标记处)

---

## 0. 结论先行

推荐 **WorkBuddy 云服务(内置 Auth + 云数据库)** 作为账号底座,前端保持零构建、走 CDN 引入;把
`store.js` 的 `read()` / `write()` 从 localStorage 改成「**云端为准 + 本地离线缓存**」;
登录方式按 **手机号验证码 → 微信扫码 → 邮箱** 的优先级逐步开放。

理由三句话:

1. 站点已经作为应用 `wbapp_Hq5OK3jMzN64v1kK3FMP1z` 发布,云服务的身份校验按 **同源 Origin** 生效
   —— 复用同一个应用 id 即零配置;自建后端反而要额外解决域名、HTTPS 与微信开放平台资质。
2. `store.js` 已经把「数据放在哪里」隔离成一层,全站读写只有一个收口 → **改造面积最小**。
3. 零运维:不买服务器、不配数据库、不管证书。

代价也必须说清:数据从「只在你自己的浏览器里」变成「在托管环境里」,而档案里有
**姓名 / 身份证号 / 手机号 / 紧急联系人电话**。所以本方案把「**敏感字段默认不上云**」定为硬红线
(§5),而不是把所有字段无脑同步。

## 1. 现状(改造前)

| 项 | 现状 |
|---|---|
| 数据存放 | 浏览器 `localStorage`,key = `marathon_platform_v1` |
| 账号字段 | `state.account = { id, nickname, avatarChar, provider: "local", createdAt }` —— 壳已经有了,恒为 `provider:"local"` |
| 界面入口 | 顶栏 `acct-chip`(文案「本地模式」)→ `openAccount()` 弹窗,目前只是只读展示 + 一句「需要先开启后端服务」 |
| 后端接入点 | `store.js` 的 `read()` / `write()`,代码里已用 `[SEAM]` 标出 |
| 构建方式 | 无 `package.json`、无打包器 → SDK 只能走 CDN `<script>`(全局 `WorkBuddyCloud`) |
| 跨设备 | 只能「导出 JSON → 另一台机器导入」 |

**结论:脚手架已经留好了,缺的只是后端和登录界面。**

## 2. 候选方案对比

| 方案 | 登录方式 | 运维负担 | 数据在哪 | 微信小程序 | 判断 |
|---|---|---|---|---|---|
| **A. WorkBuddy 云服务** | 手机验证码 / 微信扫码 / 邮箱 | **零** | 托管环境,按应用隔离 | 同一套身份可复用 | ✅ 推荐 |
| B. 自建后端(Node + Postgres) | 自己发码、自己存会话 | 服务器 + 域名 + 证书 + 备份 | 自己机房 | 需另做 | 可控但重,当前阶段不划算 |
| C. 第三方 BaaS(Supabase 等) | 需自备短信通道 / 微信资质 | 低 | 第三方 | 需另做 | 与 A 类似,但要自己去办资质 |
| D. 不做账号,只做「同步码」 | 无真正登录 | 零 | 无 | 无 | 不解决多人隔离,排除 |

> 将来若要出微信小程序,A 是唯一能同时覆盖 H5 与小程序的路线(同一套云端身份,不用迁移用户)。

## 3. 目标架构

```
┌──────────────────────────── 浏览器 ────────────────────────────┐
│  index.html                                                    │
│   ├─ engine.js      纯函数状态机(不许碰异步)                    │
│   ├─ store.js       ★ [SEAM] 读 / 写 —— 本次唯一改造点          │
│   ├─ auth.js        新增:初始化 SDK + 登录 / 登出 / 会话监听     │
│   ├─ app.js         界面层:openAccount() 换成真登录面板          │
│   └─ motion.js      动效装饰(与账号无关)                        │
└───────────┬────────────────────────────────────┬───────────────┘
            │ ① publicConfig 初始化               │ ③ 读 / 写
            │   (endpoint / publishableKey /      │   Authorization: 会话
            │    oauthRelayBaseUrl)               │
            ▼                                     ▼
┌──────────────────────── WorkBuddy 云服务 ───────────────────────┐
│  Auth 模块 ──签发会话──►  身份(userId)                          │
│  Database 模块 ──按 user_id 隔离──►  user_state 表               │
│  服务端强制 Origin 精确匹配 + 行级归属校验                        │
└─────────────────────────────────────────────────────────────────┘
            ▲
            │ ④ 未来:P2 阶段由服务端定时任务跑巡检 / 发提醒
            └── tools/notify.js(当前读本地 JSON,见 §9 待决)
```

数据流一句话:**登录拿身份 → 拉云端 state → 与本地 state 合并 → 之后每次 save 双写(云为准,本地做缓存)。**

## 4. 代码落点(逐条)

### 4.1 新增 `marathon-platform/assets/auth.js`

```js
// 全站初始化一次,所有模块复用同一个 client 实例
var cloud = WorkBuddyCloud.createWorkBuddyCloud({
  endpoint: publicConfig.endpoint,             // 必须来自 publicConfig,不许硬编码、不许读 location
  oauthRelayBaseUrl: publicConfig.oauthRelayBaseUrl,  // web 端微信扫码登录必需,缺了会运行时报错
  publishableKey: publicConfig.publishableKey
});
```

`index.html` 在 `</body>` 前追加 CDN 引入(必须 `@dev`,不能用 `@latest`):

```html
<script src="https://cdn.jsdelivr.net/npm/@tencent-ai/workbuddy-cloud-sdk@dev/lib/index.global.js"></script>
```

### 4.2 `store.js` 的三处改动

1. `read()` / `write()` **保留函数签名**,内部改走云端;另加语义明确的 `pull()` / `push()`。
2. 新增**离线写队列**:断网时写本地,恢复联网后回放(避免「改一笔就失败」)。
3. 全站 `S.save()` 的调用点补 `await` / `.then` —— **这是本次最大的回归风险**,见 §8。

### 4.3 云端数据表

先用 **单表 JSON blob** 起步:

| 表 | 字段 | 说明 |
|---|---|---|
| `user_state` | `user_id`(主键) / `payload`(JSON) / `updated_at` | `payload` 结构与现有 `state` 一一对应 |

好处是迁移成本最低、与 `store.js` 的 `normalize()` 直接对齐;等真要做跨用户统计 / 分享时再拆成
`watches` / `checklists` / `profiles` 多表。**不要一上来就拆表。**

体量估算:单用户 state ≈ 10–40 KB(60 场关注 + 34 字段档案),1000 用户 ≈ 40 MB 量级,很轻。

## 5. 隐私红线(本方案的核心约束)

| 数据 | 是否上云 | 理由 |
|---|---|---|
| 关注清单 / `userStatus` / 材料勾选 | ✅ 上云 | 无敏感信息,正是跨设备要同步的东西 |
| 偏好设置(提醒通道、提前天数) | ✅ 上云 | 同上 |
| 档案:姓名 / 性别 / 出生 / 城市 / 成绩 / ITRA 分 | ⚠️ 可选,默认关 | 属个人数据,由用户显式开关 |
| **身份证号 / 手机号 / 紧急联系人电话** | ❌ **默认不上云** | 一旦上云就变成「托管环境里存了身份证号」,风险与收益不成比例。仅当用户显式勾选「我需要云端保管证件信息」时才同步,并在界面明确标注 |

外加三条不可让步的:

- 前端**永远不持有任何长期密钥**。只有 `publishableKey`(它本身不带权限,靠服务端 Origin 校验)。
- 任何读写**必须带身份约束**(`user_id` = 当前会话用户),谁都不能读到别人的数据。
- 日志、导出文件、错误上报**都不得打印**证件号 / 手机号 / 会话令牌。

## 6. 首次登录的合并策略

登录不是「清空换一份」,而是**合并**。规则写成引擎里的纯函数 `ME.mergeStates(local, cloud, opts)`,
这样能被回归测试覆盖,也不会漂移。

| 数据 | 合并规则 |
|---|---|
| `watching` | 按 `raceId` 取并集;同一场冲突时取 `updatedAt` **较新**的一条(用户刚手动改的「已缴费」不该被旧的云端值覆盖) |
| `checklists` | 并集(勾过就是勾过) |
| `profile` | 逐字段:一边为空取另一边;两边都非空且不同 → 弹面板让用户选 |
| `custom`(自建赛事) | 按 id 取并集 |
| `settings` | 本地优先(提醒偏好常与设备相关) |

三种入口情况:

| 情况 | 处理 |
|---|---|
| 云端空、本地有 | 直接把本地整份上传,不打扰用户 |
| 本地空、云端有 | 直接拉云端覆盖,提示「已从云端恢复 N 场关注」 |
| 两边都有 | 走合并 + 展示一份差异摘要让用户确认(不静默合并) |

## 7. 分期与 gate

| 阶段 | 内容 | Gate(做到才算过) |
|---|---|---|
| **P0 身份** | `auth.js` + CDN 引入 + 登录面板 + 顶栏昵称;**数据仍留本地** | 能登录、能登出、刷新后会话还在;登出后回到本地数据且不丢 |
| **P1 上云** | 单表 blob 读写、离线缓存、`mergeStates` | 换设备 / 换浏览器登录能看到同一份关注;断网改动在恢复后不丢 |
| **P2 服务端** | 拆表 + 邮件 / 微信提醒改由服务端跑(密钥只在服务端) | 电脑没开机也能收到邮件;巡检不再依赖某台机器开机 |
| **P3 协作** | 关注清单分享、跑团 / 观赛小组 | — |

**P0 就能独立上线**,不影响现有本地用户 —— 这是选择分期而不是一次做完的主要原因。

## 8. 回归与兼容

- **引擎不许碰异步**:`engine.js` 保持纯函数,异步只留在 `store.js` 边界。回归测试 A 段(引擎防漂移)、
  B 段(数据层)因此不受影响。
- **C 段(界面)是按类名计数断言的**。新增登录 UI 必须避开被计数前缀:
  `kpi` / `lib-card` / `kt` / `kind-sec` / `ks-desc` / `k-tag` / `lc-dist` / `race ` / `kd"` / `field"`。
  建议用新的 `acct-*` 命名空间。
- `S.save()` 变 async 之后,`tests/regression.js` 里对 store 的同步调用需要加一个小 helper
  (如 `await flush()`),并**补一条「本地模式同步链路」的回归用例**,防止本地版被改坏。
- 迁移兼容:`normalize()` 已经能吃缺字段的旧数据 → 云端拉回来的老副本不会炸。

## 10. 一句话总览

> 账号体系的难点不在「怎么登录」,而在**「本地已有的那份数据怎么安全地变成云端数据」**。
> 所以本方案的重心放在 §5 隐私红线与 §6 合并策略上,登录本身反而是最省事的一环。
