# 赛事跟踪台(马拉松 / 路跑 + 全球越野赛)

关注你想要的赛事,系统自动盯着它的**报名开放 / 报名截止 / 抽签公布 / 缴费截止**,
在真正需要你行动的那一刻把你叫起来。

**当前版本:本机优先 + 云端同步(P1 已落地)** —— 关注清单 / 材料勾选 / 偏好设置 / 自建赛事
可登录后跨设备同步;**档案里的姓名 / 身份证号 / 手机号 / 紧急联系人只留本机,不同步上云**。
微信扫码 / 跑团共享等更强能力待后续阶段(接入点见下文)。

收录范围:**24 场马拉松 / 路跑 + 36 场全球越野赛,共 60 场**
(2026–2027 赛季,含 UTMB 总决赛与世界系列赛、世界越野大满贯 WTM、西部州 100 / 硬石 100 等经典超长越野)。
两类赛事在赛事库、我的关注、看板与每日邮件里**全程分类展示**,不混在一个列表里。

## 目录结构

```
marathon-platform/
├── index.html              应用外壳(五个视图)
├── assets/
│   ├── engine.js           ★ 状态引擎 + 赛事种子数据(纯函数,零 DOM)
│   ├── store.js            数据层/存储适配器
│   ├── app.js              界面层
│   ├── styles.css          样式 + 全部 CSS 动画
│   ├── auth.js             本地身份层(昵称/邮箱存 localStorage)
│   ├── cloud.js            云端同步层(P1):真实云账号 + 单表 blob,换设备同步
│   └── motion.js           动效装饰(计时器/进度条/KPI 数字),可整个删除
└── README.md
```

依赖顺序固定:`engine.js → store.js → auth.js → cloud.js → app.js → motion.js`。六者都不需要构建步骤,
直接开 `index.html` 即可运行。`motion.js` 是**纯装饰层** —— 它不读写存储、不碰引擎,
删掉它页面功能完全不受影响。

## 界面风格:跑道 / 田径

主题就是跑步,视觉语言取自体感赛场:

| 元素 | 表现 |
|---|---|
| 顶栏 | 深色沥青渐变 + 循环掠过的扫光 + 底部滚动分道虚线;品牌圆标带脉冲光环 |
| 计时器 | 顶栏一枚每秒走动的跑步表,等宽字体 + 闪烁指示点 |
| Hero | 底部渐隐的跑道分道线;一个**四肢循环摆动的跑者剪影**沿赛道循环跑过 |
| 赛道播报 | 未来 60 天的关键节点横向滚动播报,悬停暂停 |
| 卡片 | 号码布式徽标 + 等宽斜体计时数字;悬停上浮并有一道速度残影横扫 |
| 进度条 | 底下是分道刻度,填充里跑过一条流光 |
| 入场 | 卡片按 `nth-child` 依次延迟升起,形成「起跑」错位感 |
| 数字 | 时间与计数统一 `font-variant-numeric:tabular-nums`,读起来像计时器 |

**全部动效为纯 CSS 关键帧,不引入任何前端库。** 系统开启「减少动态效果」
(`prefers-reduced-motion`)后,所有动画与过渡一次性关停,跑者定格居中 —— 这是硬要求。

改视觉请**只改 `assets/styles.css` 并保留既有类名**:回归测试 C 段是按类名计数做断言的,
改类名会让一批断言同时变红。新增装饰元素的命名要避开 `kt` / `k-tag` / `kd` / `kpi` /
`race ` / `lib-card` 这些会被计数的前缀。

## 为什么要把引擎单独拆出来

`assets/engine.js` 是**唯一一份**状态判断逻辑与赛事目录,被四个地方共用:

| 使用方 | 怎么用 |
|---|---|
| 本网站 | `<script src="assets/engine.js">` → `window.ME` |
| 每日巡检脚本 `tools/digest.js` | `require('../marathon-platform/assets/engine.js')` |
| 邮件推送 `tools/notify.js` | 经由 `digest.js` 间接使用同一份引擎 |
| 后续微信小程序 | `require` 同一份文件 |

这么做的原因很实际:**如果状态判断被写两遍,迟早会漂移** —— 出现"网页说待缴费、
提醒邮件说已截止"这种最要命的错误。共用一份文件,从结构上就不可能漂移。

已完成两轮防漂移对照:

1. 新引擎与原单文件版本在 **1152 组**(24 场路跑 × 6 种用户状态 × 8 个时间点)对照中差异为 **0**;
2. 加入越野赛后再次对照,路跑 1152 组**无真实漂移**,仅有的 2 组差异全部来自新增的
   `opendeadline` 状态(修正了旧逻辑把"已开放但无截止日"误判为"窗口待公布"的问题)。

改状态判断时,只改 `engine.js`,其他一切自动跟随。

## 状态引擎的 15 个状态

| key | 含义 | 触发条件 |
|---|---|---|
| `pay` | **待缴费** | 已中签,且缴费截止未过 —— 最容易丢名额的环节 |
| `drawdone` | **结果已公布·待确认** | 抽签日已过 7 天内,用户还没更新状态 |
| `closing` | 即将截止 | 报名窗口 3 天内关闭 |
| `soon` | 即将开放 | 7 天内开放报名 |
| `open` | 报名中 | 窗口开放中,截止日已知 |
| `opendeadline` | **报名中·未设截止日** | 已开放,但官方没公布截止日(售罄即止) |
| `waitdraw` | 待抽签 | 报名已截止,抽签日未到 |
| `pending` | 已报名·待结果 | 同上,但用户已标记"已提交" |
| `racing` | 已锁定·待比赛 | 报名环节结束,进入赛前准备 |
| `notopen` / `unknown` | 未开放 / 窗口未记录 | 官方尚未公布报名时间 |
| `closed` / `lost` / `done` / `skipped` | 已截止 / 未中签 / 已完赛 / 已放弃 | 终态 |

两个状态是**专门为真实世界的坑**而加的:

- **`drawdone`** —— 抽签结果公布时用户往往不知道,而中签后缴费期通常只有 3–7 天。
  没有这个状态,系统会把这种情况错误地显示成"已截止",把最关键的警报埋在了一个
  看起来无事发生的状态下面。
- **`opendeadline`** —— 越野赛(以及国内先到先得的路跑)**极其常见**:
  公告了开放日却永远不说截止日,名额售罄即止。旧逻辑要求"开放日与截止日同时存在"
  才判定"报名中",于是这类赛事全部掉进"窗口待公布",把一个正在开放的窗口写成了还没开放。
  这类赛事在 60 场里有 4 场,占比不低。

## 越野赛扩展:为什么不能复用马拉松那套

越野赛与路跑在三个地方完全不同,所以引擎里单独成支:

| 维度 | 马拉松 / 路跑 | 越野赛 |
|---|---|---|
| **赛制** | 抽签 / 先到先得 / 成绩达标 | 抽签 + **ITRA 表现分门槛** / **跑石(Running Stones)+ UTMB 指数双门槛** / 资格赛制 |
| **资格** | 24 个月内的全马或半马成绩 | **同类距离的山地完赛记录**(路跑成绩通常不被接受) |
| **材料** | 体检报告、完赛证明 | 追加**强制装备**(头灯+备用电池 / 救生毯 / 冲锋衣 / 哨子 / 水袋 / 备用口粮 / 急救绷带)、夜间行进能力、换装包规划 |

引擎据此新增:

- `kind: "road" | "trail"` 与 `kindOf()` / `KIND_LABEL` / `SEED_ALL`;
- `tier`: `utmbfinal`(UTMB 总决赛)/ `utmbws`(UTMB 世界系列赛)/ `wtm`(世界越野大满贯)
  / `wmtrc`(世界锦标赛)/ `classic`(经典超长越野)/ `std`;
- 新赛制 `stones`(跑石抽签);
- `itraMin` 字段 —— 已收录赛事中 **柴古唐斯括苍(260 分起)与熊猫蜀道山(249 分起)**
  有官方公布的 ITRA 阶梯门槛,分数不够直接报不上;
- `maxDistKm()` —— 从组别文本里解析最长距离,与档案里的"最长越野完赛"比较,
  距离不够时提示"先补齐距离或改报短组别";
- 档案新增 4 个字段:`trailMax` / `trailMaxRace` / `trailMaxDate` / `itra`。

## 分类显示:马拉松与越野赛全程分开呈现

两类赛事不是同一个东西,所以**从界面到邮件一律分类,不混在一个列表里**:

| 位置 | 分类方式 |
|---|---|
| **赛事库** | 顶部类型切换条 `全部类型 60 / 马拉松·路跑 24 / 越野赛 36`;选「全部」时列表**分成两个区块**,每区有标题、场次数和一句话说明(赛制 / 资格 / 材料差在哪)。选了某一类就只渲染那一区 |
| **我的关注** | 同样的类型切换条,可按类筛选;分组标题(需要行动 / 待开放 / 已结束)在**两类混合时**额外标出 `马拉松·路跑 3 · 越野赛 2` |
| **看板** | 横幅下方一条**类别速览**:两类各关注了多少场、其中几场正在报名窗口里 |
| **提醒与导出** | 推送预览每条带类型标签;日历事件沿用引擎的越野赛附加说明 |
| **每日邮件** | 摘要表每行带 `[越]` 前缀,并给出「路跑 X 场 / 越野赛 Y 场」分类统计 |
| **详情弹层** | 标题下方直接标出「越野赛 / 马拉松 / 路跑」,越野赛事额外显示组别距离 |

颜色也一并区分:路跑用青绿、越野用土黄,卡片上的圆点、标签、分区标题都遵循同一套色。

分类的判定**只来自引擎的 `kindOf()`**,界面不自己猜 —— 这样以后新增赛事类型
(例如 Skyrunning、山径徒步)时,只需在引擎里加一个 `kind`,界面自动多出一区。

## 提醒的哲学:只在真的需要行动时打扰

`tools/digest.js` 里的"紧急"集合 = `pay` + `drawdone` + `soon` + `closing`,
即**有明确时间窗、错过就没了**的事件。

`opendeadline`(长期开放、未设截止日)被**故意排除在紧急之外** ——
它会长期挂着(有的已开放数月,例如越南高地越野赛),若也计入紧急,
邮件将永远无法安静下来,天天为同一场赛事报警,反而把真正的截止日淹没。

它的待遇是:摘要里单独成节、邮件正文里始终列出、窗口概览里各占一行,
**只是不单独触发发信**。

## 接后端:只有一个改动点

`assets/store.js` 里,`read()` 和 `write()` 两个函数是**唯一**需要替换的地方:

```js
/* ---------------------------------------------------------------- [SEAM] */
function read()  { ... localStorage.getItem ... }
function write(o){ ... localStorage.setItem ... }
/* --------------------------------------------------------------------- */
```

换成网络调用即可。界面层完全不知道数据放在哪里,一行都不用改
(如果改成异步,把调用点补上 `await`)。

### 接后端后会解锁的能力

| 能力 | 现在 | 接后端后 |
|---|---|---|
| 微信扫码 / 一键登录 | ✗(P0) | ✓(P1 仅手机/邮箱 OTP;微信扫码待后续) |
| 换设备继续用 | ✗(P0) | ✓(P1 已落地,单表 user_state 同步) |
| 多人各自关注、互不可见 | ✗(各存各的浏览器) | ✓ |
| 邮件摘要 | ✗ | ✓ |
| 微信提醒 | ✗ | ✓ |

> **进度更新(P1 已落地):** 上面的「换设备继续用」与「多人各自关注」已通过云端账号实现,
> 当前用单表 `user_state`(JSONB)承载关注/勾选/设置/自建赛事,**证件类字段仍留本机**。
> 微信扫码与多表拆分(P2)待后续。

数据库(长期目标 P2)需要这几张表(按用户隔离):

```
users          id / openid / nickname / createdAt
profiles       user_id / <33 个档案字段,含 4 个越野字段>
watchlist      user_id / race_id / status / addedAt
checklists     user_id / race_id / item_key
sub_credits    user_id / template_id / remaining   ← 小程序一次性订阅的额度账本
notify_log     user_id / race_id / kind / channel / sentAt
```

`sub_credits` 这张表是关键。微信小程序的订阅消息**只有一次性订阅**可用于
工具/体育类目(长期订阅仅限政务、医疗、交通、金融、教育),所以提醒不能设计成
"想推就推",必须是**攒额度 → 关键节点消耗**:

1. 用户在小程序里做正经操作时(点「关注这场赛事」、保存档案),顺手调
   `wx.requestSubscribeMessage` 攒下授权;
2. 服务端按模板 ID 记账,每次下发扣一次;
3. 额度耗尽时降级到邮件或日历提醒。

最佳搭配是**认证服务号**:用户关注后,模板消息可长期、多次下发
(日上限 10 万次),不受一次性额度限制。这应当作为主通道。

## 数据可信度

赛事日期都带可信度标签,请以此判断能不能当真:

| 标签 | 含义 |
|---|---|
| 官方公告 | 组委会已正式发布 |
| 媒体多源 | 多家媒体一致报道,但未见官方原文 |
| 按往年推算 | 依历年规律估算,**很可能不准** |
| 手动录入 | 你或他人手工添加 |
| 待公布 | 官方尚未公布 |

越野赛的报名窗口**公布得普遍比路跑晚**,"待公布 / 窗口未记录"占比高属正常
(60 场里有 31 场处于该状态),这不是数据缺失,而是越野赛的常态节奏。

**最终一律以组委会官方公告为准。** 系统只负责让你不错过,不负责替你确认日期。
